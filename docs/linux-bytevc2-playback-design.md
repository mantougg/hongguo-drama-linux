# Linux ByteVC2 播放、下载与转码设计

状态为待实施。设计基线为 Linux `1.74.13`（`237d653`），目标平台为 Linux x86_64。本文供接手开发与验收使用。

## 目标和实施顺序

1. **先交付可播和可下载。** 红果 App 只有 ByteVC2 可用时，使用随包 Librempeg 将完整分集转成 H.264。在线播放、下一集预取和手动下载共用同一转换逻辑与并发预算。现有 H.264、HEVC 和其他来源沿用原路径。
2. **再验证核显编码。** 在 ByteVC2 的 CPU 解码后接 Intel VAAPI H.264 编码。通过速度、体积和画质门槛后再启用自动选择，CPU 路径始终可用。
3. **用连播数据调预取。** 首版先让下一可播集提前准备，切集时接管同一任务。交付后根据取源、下载、排队、转换和首帧耗时调整策略。

libmedia 的 H.264／HEVC CPU 直接播放作为独立评估项。后续可在硬解不可用的 Linux 环境验证 1080p 播放、拖动、音画同步和 CPU 占用，再决定是否接入。本设计聚焦 App 取到 ByteVC2 后的媒体处理与 Linux 分发，沿用现有取源签名、主备恢复、窗口和播放器架构。

## 已验证的依据

## 1. 取源与画质

实现入口是 `fetchAppPlayUrl` 和 `fetchPlayUrlSingle`。在已确认支持 ByteVC2 的 Linux 播放和下载链路启用该候选，取源缓存要区分候选策略，或确保同一缓存入口的能力在进程生命周期内固定。保留当前的精确分集匹配、HTTPS 域名限制、请求头、备用地址去重和清晰度校验。 [App 取源](../src/native/app-source.js) · [取源入口和错误映射](../src/native/hongguo.js) · [画质规则](../src/native/download-quality.js)

| 场景 | 选择规则 |
| --- | --- |
| `auto`，同时有可用 H.264／HEVC 和 ByteVC2 | 先在 H.264／HEVC 中按现有规则选最高实际分辨率，保留同档变体。即使 ByteVC2 尺寸更高，也先用兼容原片。 |
| 指定 `720p` 或 `1080p` | 先按现有短边像素下限和排序选择 H.264／HEVC。没有满足要求的可用原片时，再在 ByteVC2 中按同一尺寸规则选。 |
| 只有满足要求的 ByteVC2 | 选择 ByteVC2。同档备用地址沿用现有尝试上限。 |
| 仅有低于指定画质或尺寸不可确认的片源 | 返回现有清晰度类错误，保持用户选择。 |
| 只有其他未知编码 | 返回 `UNSUPPORTED_CODEC`，提示根据实际支持能力生成。 |

这里的可用候选指完成模型、画质、地址和加密信息校验的变体。已选兼容片源遇到 CDN 超时或传输中断时沿用既有媒体重试。ByteVC2 也必须由本集模型提供，保留原模型的媒体标识、正数且有限的完整时长、有效宽高与加密信息。响应中的分集 `vid` 与模型内的媒体标识可能是不同格式，应分别用于分集匹配和媒体身份校验。候选向主进程标记 `codec: 'bytevc2'`，携带 `width`、`height`、`duration`，以及现有 `contentKey` 等字段。明确未加密的候选可走同一转换，其他候选须有可验证的 CENC 解密信息。

## 2. 完整媒体的准备和发布

主进程在分派媒体处理时先识别 ByteVC2，再进入原有 CENC、旧式加密或明文分支。新增独立转换模块，用于三个调用入口。 [在线准备与手动下载入口](../main.js)

| 入口 | 处理方式 |
| --- | --- |
| `prepareManagedPlayback` → `prepareDiskEpisode` | 沿用现有磁盘准备、`requestMedia`、进度通知和流式下载上限。完整下载到受管临时文件后，把 ByteVC2 交给转换模块，验证后作为该分集的 `video.mp4`。 |
| 非磁盘 `prepare-online-play` | 选中 ByteVC2 时同样先生成受管的 H.264 文件，再通过现有在线媒体协议提供分段读取。已有的 H.264／HEVC 内存和直连路径继续按现行规则处理。 |
| `executeHongguoDownload` | 优先复用同分集、同来源且符合画质的已验证缓存。需要转换时使用共享任务；下载副本继续走 `verifyDownloadQuality` 和 `publishDownloadFile`，按现行规则发布到用户选择的目录。 |

转换模块接收受管本地输入、独占临时输出、验证过的媒体参数、取消信号和进度回调。Librempeg 从本地文件读取，有 CENC 时用已验证的密钥在同一次进程中解密并解码。首版以原尺寸 H.264 `yuv420p` 为输出，采用上游 x264 `veryfast`／`CRF 23`，AAC 音轨复制，保留原有无音轨状态。遇到组件无法正确保留的音频编码时明确失败。进程只使用本地文件协议，沿用主进程的媒体访问与地址约束。密钥、签名和带参数的媒体地址只用于当前请求和媒体进程，排除在日志、IPC 进度、缓存清单和交付测试素材之外。

输出先写临时文件。成功退出后，复用 FFprobe 校验 H.264 视频轨、原始分辨率、画质下限、音轨及完整时长。校验视频轨的时长，容器总时长只作为辅助，首版允许最多 1 秒封装误差。转换进度按已输出媒体时长计算，通过校验和发布后才标记为完成。受管播放保留现有单集 1 GiB 和窗口限制，输入、输出与临时文件同时占用的空间纳入磁盘预算。手动下载遵守目标目录和现有发布规则。失败、退出、切换或重试时清理本次未完成的输出，已完成的用户下载沿用现有保护规则。 [缓存与大小限制](../src/native/playback-cache.js) · [下载校验与发布](../main.js)

## 3. 任务、预取和缓存

- **单任务预算。** ByteVC2 播放、预取、下载共用一条转换队列，同时最多运行一个转换进程。CPU 路径从上游已验证配置起步，解码与编码各 2 线程，滤镜和 x264 lookahead 各 1 线程。排队优先级为当前播放、下一可播集、普通下载，同级按进入顺序。正在运行的转换可被同一集前台接管并同步进度，优先级变化保持原进度。
- **按身份合并。** 基于来源、剧集、分集、画质和实际输入身份复用结果。沿用 `onlinePreparing`、`onlineSessions` 和现有缓存检查，以可比较的身份确认可以共用时才加入在途转换。不同画质的请求分别校验，生成的受管文件和最终手动下载文件保持各自的生命周期。强制重取有新的任务代次，旧代次的结果只交给仍合法持有它的消费者。
- **按消费者取消。** 单个播放窗口、后台预取或下载取消时先解除自己的等待。最后一个消费者离开时，从队列移除或终止转换，等待子进程退出再清理临时文件。切剧、跳集、改画质、退出和失败都要释放队列。使用现有请求 ID 与持有关系过滤迟到的进度和结果。
- **预取从下一集开始。** 前后各 5 集仍是缓存保留窗口。主动启动 ByteVC2 转换时先准备下一可播集，跳过锁定集，较远集沿用现有取源或下载调度并推迟转换。切到正在准备的下一集时提升同一个任务。后台准备过程在当前集继续播放时保持静默。
- **只发布完整结果。** 沿用受管播放缓存和磁盘文件的读者保护。保存 `codec: 'h264'`、实际尺寸和原来源 `mediaSource: 'app'`。如需诊断，用可选字段另存原编码、转换方式和处理版本。旧缓存缺少这些字段时按现行身份及文件校验规则读取。输出确认可直接播放后正确设置 `directH264`，兼容模式可以复用它。 [现有缓存实现](../src/native/playback-cache.js) · [现有切集和预取计划](linux-playback-optimization-plan.md)

## 4. VAAPI 加速与错误处理

核显路径仍使用 Librempeg 的 ByteVC2 CPU 解码，将原始帧转成 `nv12` 后上传到 Intel 设备，用 `h264_vaapi` 编码。设备发现沿用 `pickPlaybackVaapi` 的 DRM 节点和实际编码探测思路，探测对象为本次使用的加速组件。用稳定路径或动态探测识别设备，支持没有 DRM 节点、权限不足和驱动初始化失败的环境。 [现有 VAAPI 探测](../src/native/playback-vaapi.js) · [现有兼容转码实现](../main.js)

同一任务可先试一次 VAAPI。设备、编码或输出验证失败时，清理失败输出并用同一份下载输入回退一次 CPU；已经取消或磁盘空间不足时直接结束。网络中断和媒体 URL 失效沿用现有有界媒体恢复。缺少解码组件、确认不兼容、媒体元数据无效、两条转换路径均失败时，提示具体原因并结束本轮。保持原有空响应和匿名会话冷却策略。

沿用现有在线和下载进度通道。在线至少区分取源、重连、缓冲、等待转码、正在转码、可播和失败。下载继续使用现有任务状态，可用附加阶段字段表达排队或转换。前台接管时回放最新进度。日志按同一请求标识汇总取源、下载、排队、转码、校验和首帧耗时，以及实际编码器、缓存命中、输出字节数和错误类别。 [播放器进度与预取](../src/components/Player.jsx) · [IPC 桥接](../preload.js) · [App 取源恢复规则](linux-app-source-recovery-plan.md)

**核显默认启用门槛。** 建议用至少三段内容不同的 1080p ByteVC2 样本做成对复测，包含第 18、19 集；用同一输入和线程预算，交替运行顺序，分别记录转码耗时、累计 CPU 时间、文件大小和相对于解码原片的 SSIM。首轮目标是中位转码耗时下降至少 20%、中位 CPU 时间下降至少 30%、每段输出不超过 CPU 版的 1.25 倍、每段 SSIM 相比 CPU 版下降不超过 0.005。门槛用于决定默认参数和是否启用加速。达不到时仍可交付 CPU 兼容路径，将加速保留为开发验证项。

## 5. Linux 构建与分发

以原上游 `v6.2` 的构建脚本为参考，固定 Librempeg `cb1f8f3eef84999e61b27e2d44664858179bc240` 和 x264 `b35605ace3ddf7c1a5d67a2eb553f034aef41d55`，核对源码及产物摘要。CPU 辅助程序随 Linux x64 包放在 `resources/bin`，开发态放在同平台的 `build/ffmpeg/linux-x64`，用绝对路径启动。保留项目现有的 FFmpeg／FFprobe，用于通用媒体处理和输出校验。将二进制、许可正文、构建参数与对应源码归档纳入同版发布清单。 [上游固定源码构建](https://github.com/jackotom/hongguo-drama/blob/v6.2/scripts/build-librempeg-source.sh) · [上游媒体工具许可说明](https://github.com/jackotom/hongguo-drama/blob/v6.2/build/ffmpeg/LIBREMPEG-NOTICE.txt)

核显阶段优先使用独立的可选加速构建，避免将 `libva` 运行库变成 CPU 解码组件的前置条件。构建基线与现有 Linux 包兼容；在干净环境检查 ELF 架构、动态库、执行权限和实际 `bvc2` 解码能力。验证有 `libva` 和 DRM 的设备能加速，无这些依赖时 CPU 组件仍能完整工作。正式包检查新增的辅助程序和许可文件；安装与原位更新检查覆盖新包、旧版升级、缺失新包组件的失败处理及旧资料保留。包体和对应源码摘要随现有发行产物生成。 [包配置](../package.json) · [打包入口](../scripts/package-linux.js) · [发行工作流](../.github/workflows/linux.yml) · [更新包验证](../scripts/check-linux-update-bundle.cjs)
